Run the strong codecs.Keep the smallest.

HyperPress is a meta-compressor in pure Python. It tries xz, bz2, zlib and zstd configurations on your data one after another and returns whichever output is smallest.

len(compress(d))≤ min(xz-raw-9e, bz2-9, zstd-19*) + 16

Holds for the default level="best". *zstd-19 counts only where the standard library has it (Python 3.14+). level="fast" has no size guarantee.

Never meaningfully worse than the best single codec

Every codec has data it is good at. xz wins on binaries and structured files, bz2 on plain prose. HyperPress always runs the plain xz-raw-9e, bz2-9 and (on Python 3.14+) zstd-19 on the whole input, so it cannot lose to them by more than its own container header.

On top of that it tries variants that sometimes win: a delta filter for sampled data, an x86 BCJ filter for executables, LZMA2 with tuned lc/lp/pb, a word-dictionary TEXT transform before bz2 or xz, and a BLOCKS path that splits the input and preprocesses each block. A deterministic probe on samples decides which variants are worth running in full. A STORED fallback means incompressible data grows by the header only.

    Smaller costs time

    HyperPress runs many candidates in sequence, so at the best level it compresses slower than xz -9e or zstd -19 alone. The fast level tries at most five cheap candidates and is quicker, but its output is noticeably larger and carries no size guarantee.

    The HPRX v2 container, byte by byte

    A few header bytes describe how to decode the payload. Filter parameters follow from the method id, so nothing else is stored.

    Real output of compress() for a short sample.

    In BLOCKS mode the method byte is replaced by a block count, and each block carries its original size, compressed size, preprocessor and backend. The whole-file CRC32 covers all of them.

      Hostile input gets an error, not a crash

      Decompression validates everything it reads and caps how much memory a bad stream can claim.

      Memory bound for a rejected stream

      Peak allocation beyond the input itself, relative to max_output_size (the cap). Bounds from the v2 specification.

      Your limitcap
      zlib, bz2, STORED, BLOCKScap + 64 KiB
      LZMA paths (dictionary next to output)2 × cap + 64 KiB
      TEXT transform (inner stream plus output)2.25 × cap + 64 KiB
      one cap64 KiB slack (not to scale)

      A declared size above the cap is rejected before decoding starts. The cap never breaks a valid stream: every output decodes with max_output_size equal to the original length.

      • CRC32 of the original

        Checked after decoding. A wrong checksum, a size mismatch or trailing garbage is an error.

      • One exception type

        Bad input raises HyperPressError, a ValueError subclass, and nothing else. Validation never uses assert, so it also holds under python -O.

      • Streaming with a hard cap

        lzma, zlib and bz2 decode incrementally with a maximum length, so a bomb with a lying header stops at the limit.

      • Deterministic and backward compatible

        Same input and same Python version give the same bytes. v1 streams still decompress.

      Two calls

      shell
      pip install "git+https://github.com/BEKO2210/HyperPress@v2.0.1"
      python
      from hyperpress import (
    compress, decompress, HyperPressError)

# level="best" (default): size guarantee
blob = compress(data)
# faster, no size guarantee
quick = compress(data, level="fast")

try:
    data = decompress(
        blob, max_output_size=64 << 20)
except HyperPressError:
    ...  # corrupt, truncated, oversize
      • compress(data, level="best", verbose=False) returns an HPRX v2 stream. level is "best" or "fast".
      • decompress(data, max_output_size=1 << 30) returns the original bytes or raises HyperPressError.
      • Python 3.8 or newer, standard library only. A stream that used zstd needs Python 3.14+ to decode.
      • Memory grows with input size, since candidates are compressed in memory.

      Version 1 advertised wrong numbers

      An independent audit found that the v1 claims did not hold. They were all removed, and v2 was rebuilt around a guarantee that the test suite and the CI benchmark check.

      No compressor wins on all data. HyperPress is a safety net on top of existing codecs, not a better codec.
