Technical Whitepaper

HyperPress: An Adaptive
Meta-Compressor

A thin selection layer over established codecs (LZMA2, bzip2, zlib, zstd) with a checkable size guarantee — and an honest account of what it does not do.

Section 01

Abstract

HyperPress is an adaptive meta-compressor. It is not a new compression algorithm: it runs several established codec configurations on the input, one after another, and keeps the smallest result. Version 2 guarantees len(compress(d)) ≤ min(xz-raw-9e, bz2-9, zstd-19*) + 16 bytes for every input at the default best level (* only when the standard library provides zstd, Python 3.14+). On real data it is often slightly smaller than the best single codec thanks to delta and x86 filters, LZMA lc/lp/pb tuning and a block path for sensor-like data; on other data it merely ties.
Correction of v1 claims. An independent audit found the v1 marketing figures (“92.3% / +23% vs LZMA”) invalid: they were measured on self-generated repetitive data, subtracted the container header (“netto”), counted ties as wins, did not run LZMA at its strongest setting, and on real files v1 was about 20% worse than plain xz -9e. The claim that candidates are tried in parallel was also false; they are tried sequentially. This document replaces those claims. No compressor wins on all data.
Section 02

Motivation & Problem Statement

Traditional compression algorithms apply a single strategy to all data. zlib (DEFLATE) excels at text with its LZ77+Huffman approach. LZMA uses large dictionaries and range coding, ideal for structured binaries. bzip2 leverages BWT for redundant data. Yet no single algorithm is universally optimal.

Real-world data is heterogeneous. A single file may contain:

  • Text regions with high character redundancy
  • Binary headers with structured byte patterns
  • Sensor readings with strong delta correlation
  • Sparse sections dominated by null bytes
  • High-entropy regions that are incompressible
Core idea: instead of betting on one codec, try several and keep the smallest output. Because the plain xz-9e, bz2-9 (and zstd-19) results are always among the candidates, the output can only exceed the best of them by the container header (at most 16 bytes). Whether any candidate wins by a meaningful margin depends entirely on the data.
Section 03

System Architecture

HyperPress v2 builds two kinds of candidates and keeps the smallest. All candidates are tried sequentially; there is no parallelism.

Figure 1 — Processing Pipeline

HPRX v2 Output
Self-contained compressed stream

Stage Details

  1. WHOLE candidates: the full input is compressed by each whole-stream method (see the method table in docs/SPEC-v2.md). Filter parameters are implied by the method id.
  2. BLOCKS candidate: the block engine splits the input, profiles each block, tries preprocessor/backend combinations per block and keeps the smallest per block. It is one candidate among the others and is kept only if the whole stream is smaller.
  3. Selection: the smallest total stream wins. level="fast" tries only zlib-9, bz2-9, xz preset 6 and zstd-3 (if available), with no block path.
  4. Output: HPRX v2 header with whole-file CRC32, then the payload.
Section 04

Block Analysis (BLOCKS path)

In the BLOCKS candidate, each block is profiled using 6 numerical features that guide preprocessing selection:

Feature 1

Shannon Entropy

Measures information density. Range: 0.0 (constant) to 8.0 (random). Low entropy indicates high compressibility.

Feature 2

Delta Entropy

Entropy of byte-to-byte differences. Low delta-entropy indicates sequential correlation (sensor data, audio).

Feature 3

Null Ratio

Fraction of zero bytes. High null-ratio suggests sparse data ideal for RLE preprocessing.

Feature 4

Text Ratio

Fraction of printable ASCII bytes. High values indicate text data suited for BWT+MTF.

Feature 5

Structure Score

Detects repeating byte patterns at fixed intervals, indicating structured records (CSV, fixed-width).

Feature 6

Unique Bytes

Count of distinct byte values (0–256). Low unique count enables efficient Huffman/arithmetic coding.

H(X) = -∑i=0255 p(xi) · log2(p(xi))
Equation 1 — Shannon entropy calculation per block
HΔ(X) = H(xi - xi-1 mod 256)    for i = 1..n
Equation 2 — Delta entropy for sequential correlation detection
Section 05

The BLOCKS path implements 7 preprocessing transforms. Each is invertible and operates in O(n) time unless noted. They help only on data with the matching structure; on other data the plain codec usually wins. (The WHOLE path additionally uses the xz DELTA and x86 BCJ filters.)

Transform 1: Delta Encoding

Delta encoding stores the difference between consecutive bytes. For data with sequential correlation (sensor readings, audio samples), the delta stream has significantly lower entropy than the original.

d[i] = (x[i] - x[i-1]) mod 256    for i = 1..n,   d[0] = x[0]
Equation 3 — Delta encoding formula
def delta_enc(data):
    out = bytearray(len(data))
    out[0] = data[0]
    for i in range(1, len(data)):
        out[i] = (data[i] - data[i-1]) & 0xFF
    return bytes(out)

Transform 3: BWT + MTF

The Burrows-Wheeler Transform sorts all rotations of the input, grouping similar contexts together. Move-to-Front then converts the BWT output into a stream dominated by small integers, which compresses exceptionally well with entropy coders.

Transform 6: Nibble Split

Nibble splitting separates each byte into its high and low 4-bit nibbles, stored in two contiguous halves. This reduces entropy when high and low nibbles have different distributions, which is common in encoded data formats.

high[i] = x[i] >> 4,    low[i] = x[i] & 0x0F     output = high || low

Section 07

Candidate Selection

Candidates are evaluated sequentially (not in parallel) and the smallest output is kept. In the BLOCKS path this happens per block:

def race_block(block, profile):
    # Generate candidates based on block profile
    candidates = select_candidates(profile)

    best_size = len(block) + 1   # worse than stored
    best_result = None

    for (preproc, backend) in candidates:
        preprocessed = apply_transform(block, preproc)
        compressed = apply_backend(preprocessed, backend)

        if len(compressed) < best_size:
            best_size = len(compressed)
            best_result = (preproc, backend, compressed)

    return best_result

Candidate Selection Strategy

Not all 35 (7 transforms × 5 backends) combinations are tried for every block. The block profile guides selection:

  • Low delta-entropy: Delta and Delta-16 transforms are prioritized
  • High text-ratio: BWT+MTF is prioritized
  • High null-ratio: RLE is prioritized
  • High structure-score: Transpose is prioritized
  • High entropy (>7.5): Only Identity + Stored is tried (incompressible)

Typically 3 to 15 candidates are evaluated per block. At the top level, compress(level="best") additionally runs every WHOLE method and keeps the overall smallest stream, which is what yields the guarantee in the abstract.

Time Complexity

Backend CompressionO(n)Each codec pass, run once per candidate
Candidate SelectionO(c)c = number of candidates, tried sequentially

Equation 5 — Overall time complexity

Space Complexity

Candidates are compressed in memory and run one after another, so memory grows with input size (the whole input plus the best result so far plus one candidate output). Decompression never allocates more than max_output_size plus a small constant.

Limits

  • Slower than any single codec: level="best" tries every candidate sequentially. Use level="fast" for at most 4 candidates.
  • On data where one plain codec is already best, HyperPress ties it and adds a few header bytes.
  • Random or already-compressed data is stored essentially as-is.
  • zstd candidates exist only on Python 3.14+; such streams cannot be decoded on older Pythons (HyperPressError).
Section 11

Conclusions

HyperPress is a meta-compressor: a selection layer over established codecs. Its value is a checkable guarantee — never meaningfully worse than the best of xz-9e, bz2-9 and zstd-19 — plus occasional gains where a filter or parameter tuning fits the data. It is not a new algorithm and does not beat state-of-the-art codecs across the board.

Key points:
  • Size bound: len(compress(d)) ≤ min(xz-raw-9e, bz2-9, zstd-19*) + 16
  • Candidates are tried sequentially; there is no parallel racing
  • Hardened decoder: only HyperPressError on bad input, max_output_size bomb guard, whole-file CRC32
  • Zero external dependencies — Python 3.8+ stdlib only

Future Work

  • Parallel candidate evaluation: not implemented; would reduce wall-clock time
  • Cheaper candidate pruning: skip candidates that are unlikely to win
  • Streaming mode: compression of unbounded streams
